# 연구형 공모전 플레이북

대상 `type`: `research`(실험·모델 개발로 결과를 내고 그 결과를 보고서·발표로 겨루는 공모전. 리더보드 반복 제출이 없거나 적다). 대개 레벨 4다(레벨 정의는 `docs/CONTRACT.md` 5절). 전형적인 모양: 이미지 분할·분류 같은 모델을 며칠 서버로 실험하고, 예선에 1회 제출한 뒤 본선에서 오프라인 발표한다. 리더보드에 반복 제출하는 대회는 `model-competition.md`, 실험 없이 논문을 내는 공모전은 `paper.md`를 따른다. 운영자의 선례 폴더가 있으면 `data/local-rules.md`에 있다.

## 0. 첫 단계

1. `CONTEST.md`, `.harness/gate.json`, `.harness/launch-prompt.md`를 읽는다. 운영자 환경 규칙 `data/local-rules.md`(하네스 저장소, git 제외)가 있으면 먼저 읽는다(계산 장비와 선례가 거기 있다). 공고, 로그인 뒤에만 보이는 규칙·데이터 설명, 제출 서식을 `docs/form/`에 두고 요점을 `docs/RULES.md`에 원문 그대로 옮긴다.
2. 대회 메타를 SPEC.md 맨 위 표에 적는다: 과제(분할·분류·회귀·생성 등), 제공 데이터(장 수, 해상도, 분할: train/valid/test, 정답 공개 여부), 평가 지표와 방향, 제출 횟수(예선 1회 등), 제출물(예측 결과, 코드, 가중치, 결과서, 서식), 파일 용량 제한과 넘을 때의 제출 방법, 외부 데이터·사전학습 모델 허용 범위, 데이터 활용 서약(반출 금지, 종료 뒤 파기), 본선 방식(오프라인 발표 여부, 일시·장소).
3. 데이터를 내려받고 SHA-256을 `README.md`에 적는다. 원자료는 git에 넣지 않는다(`data/`는 `.gitignore`). 서버로 옮긴 사본도 해시가 같은지 확인한다.

## 1. 문제 정의와 평가 지표 해석

- 공고가 정의한 평가 지표를 코드 한 곳(`<패키지>/metrics.py`)에 그대로 구현하고, 공고 예시나 제공 정답으로 값을 맞춰 본다. 지표 구현이 하나여야 실험 간 점수를 비교할 수 있다.
- 공고가 정하지 않은 처리(정답·예측 모두에 없는 클래스, 빈 마스크, 경계 픽셀, 평균 방식: 이미지 평균인지 전체 픽셀 합인지)는 해석을 고르고 [가정]으로 `docs/RULES.md`와 결과서에 적는다. 해석이 점수를 크게 바꾸면 주최 Q&A에 묻는 질문을 사용자 묶음 질문(최대 3개)에 넣는다.
- 도메인 지식(재료·의료·환경 등 대상의 물리적 의미, 클래스가 무엇인지, 어떤 오류가 실제로 중요한지)은 DomainResearcher, 같은 과제의 선행 연구(소량 데이터 전이학습, 손실 함수, 증강, 기반 모델)는 ArticleResearcher에 맡기고 `research/`에 정리한다.
- 심사기준(`gate.json` `criteria`)이 점수 외에 방법의 타당성, 재현성, 도메인 해석, 발표를 보면 SPEC.md `SC-###`에 그 증거(어떤 실험·그림·표)를 함께 적는다.
- 점수 루프: 심사기준을 점수표 `RUBRIC.md`(템플릿 `<harness>/harness/templates/RUBRIC.md`, `<harness>`는 하네스 저장소)에 풀어 쓴다. 실험 설계·검증 설계 후보 2~3개(또는 SPEC·PLAN 초안)를 ContestJudge(stage `plan`)가 "이대로 완성하면" 예측 채점하고, 가장 높은 안의 부족분을 반영해 다시 채점한다(예측 총점이 목표 이상이 되거나 3회까지). 매번 `.harness/judge/plan-<n>.json`에 저장하고 `harness score <id> --stage plan --file <경로>`로 기록한 뒤 실험을 시작한다. 결과서 초안은 stage `draft`, 제출 직전은 stage `final`로 같은 방식으로 기록한다.

## 2. 오프라인 검증 설계(리더보드 없음)

리더보드가 없거나 제출이 1회이므로 모든 판단은 내 검증 점수로 한다. 검증 설계가 곧 실험의 신뢰도다.

- 분할 고정: 공식 분할(train/valid)이 있으면 그대로 기준 분할(fold 0)로 쓰고, 추가로 그룹 k-fold(같은 시편·합금·촬영 조건·환자처럼 서로 닮은 이미지를 한 묶음으로)를 만든다. 분할 명세(id 목록, 시드)를 `data/splits/` 또는 `splits_final.json`에 한 번 고정하고 바꾸지 않는다. 바꿔야 하면 PLAN.md에 이유를 적고 이전 점수와 비교하지 않는다.
- 누수 점검(`model-competition.md` 4절과 같음): 학습·검증 id가 겹치지 않는지, 같은 원본에서 잘라 낸 조각·증강본이 양쪽에 갈리지 않았는지, 정규화·전처리 통계를 검증 데이터로 적합하지 않았는지, 파일 이름·해상도 같은 정답과 상관된 우연한 단서가 없는지 확인하고 결과를 LEDGER `leakage_checks_*`에 남긴다.
- 검증 데이터 사용 기록: 설정 선택·후처리 문턱값을 검증 데이터로 고르면 그 점수는 독립된 새 데이터 성능이 아니다. 결과서에 "독립적인 새 데이터 성능은 아니다"라고 밝힌다.
- 공식 규칙이 "검증에서 평가한 모델로 test 결과도 제출"처럼 제출 모델을 묶으면, train+valid 전체로 다시 학습한 모델은 내지 않는다. 규칙 조항을 `FR-###`으로 옮긴다.
- 개선 판정 기준을 실험 전에 정한다: 기준 모델 대비 최소 개선 폭(시드·폴드 간 표준편차 이상), 추가 투자 기준, 사전 guard(클래스별 점수 하락 한도 등). 기준을 실험 뒤에 바꾸지 않는다.
- 학습 시드를 고정하고, 고정하지 못한 비결정성(GPU 연산 등)은 같은 구성 재학습 점수 차로 크기를 재서 적는다.

## 3. 서버 실험

- 학습·추론은 작업 맥에서 하지 않는다. 원격 GPU 서버가 기본이고, 서버가 바쁘거나 더 큰 GPU가 필요하면 클라우드 GPU를 쓴다(장비와 접속 방법은 `data/local-rules.md`). 클라우드 인스턴스는 실험이 끝나면 바로 삭제하고 삭제 시각을 LEDGER `notes`에 적는다. GPU 사용 계획과 비용 상한은 PLAN.md "용량·예산"에 적는다.
- 서버의 데이터 폴더는 본인만 읽게(권한 700) 두고, 데이터 활용 서약을 지킨다.
- 긴 실험은 대기열 스크립트(`runs_queue.sh` 같은)로 묶어 서버에서 돌리고, 감독은 주기 점검이나, 작업 환경이 orca면 Orca orchestration 워커로 한다. 실험마다 `runs/<run id>/`에 설정, 로그, 점수 파일을 남기고 결과만 맥으로 가져온다.
- 실험 루프 한 바퀴는 `model-competition.md` 1절(조사 → 가설 → 구현 → 실행 → 관문 검사 → ContestJudge 판정 → 기록 → 재계획)과 같다. 다만 제출 슬롯이 없으므로 "최고 기록과 비교"는 2절의 오프라인 판정 기준으로 한다. 같은 방향으로 3회 연속 개선이 없으면 공고·데이터 설명을 다시 읽고 SPEC·PLAN을 고친다.
- 커밋마다 변경 이유와 실험 근거를 `docs/changes/NNNN-<이름>.md`로 남긴다. 결과서의 근거가 된다.

## 4. LEDGER.md에 실험 기록

템플릿: `<harness>/harness/templates/LEDGER.md`. 레벨 4는 모든 실험과 제출을 남긴다.

- 실행 한 번에 "실험 기록" 한 행: `run_id`, 부모 실행, 커밋, 가설, 바꾼 단계, 검증 방식과 점수(평균·표준편차), 판정, 실패한 누수 점검, 계산 자원(`mac`, `server:<이름>`, `cloud:<인스턴스 id>`처럼), 실행 시간.
- 제출은 "제출 장부"에 한 행. 1회 제출 대회는 `daily_limit`을 1로 적고 `is_final_selection=true`로 남긴다.
- 덧붙이기만 한다. 행을 지우거나 고치지 않고, 정정은 새 행과 `notes`로 한다. 점수는 스크립트가 낸 값만 적고 추정해서 적지 않는다.
- 실험 요약표(`docs/experiments.md`)는 LEDGER에서 만든다. 두 곳의 수치가 다르면 LEDGER가 맞다.

## 5. 1회 제출 전 재현성 확인

되돌릴 수 없는 제출이므로 제출 패키지를 깨끗한 곳에서 다시 돌려 본다.

1. 제출 후보를 고른다: 2절 판정 기준을 통과한 실행 중 검증 점수가 가장 높은 것. 근소한 차이면 더 단순하고 재현이 쉬운 쪽.
2. 제출 패키지(예측 결과, 코드, 가중치, 환경 명세 `environment.yml`, 실행 스크립트 `predict_final.sh`·`scripts/reproduce.sh`)를 서식이 요구하는 폴더 구조로 만든다.
3. 패키지를 새 폴더에 풀고, 새로 만든 환경에서 README의 명령만으로 test 예측을 다시 만든다. 다시 만든 결과와 제출 결과를 비교한다(파일 집합, 크기·형식, 픽셀·값 차이 비율, 가중치 해시). 차이가 있으면 크기를 숫자로 적고(예: 전체 픽셀 중 다른 픽셀 수) 원인을 확인한다.
4. 형식 관문: 파일 개수·이름 규칙·이미지 크기·클래스 값 집합·압축 용량을 스크립트로 검사한다. 용량 제한을 넘는 가중치는 공고가 안내한 별도 방법(메일 등)을 SUBMISSION.md에 적는다.
5. 제출 사본에서 내부 호칭·개인 경로·비밀 키를 지운다(저장소 원본은 그대로 둔다).
6. ContestJudge(stage `final`)로 결과서·패키지를 판정해 `ready`와 목표 이상 점수를 받고 `harness score <id> --stage final --file <경로>`로 기록한다. SUBMISSION.md를 채우고 커밋·푸시 후 `harness transition <id> awaiting_approval --note "<후보 run id·검증 점수·재현 결과 요약>"`(목표 미달로 내야 하면 `--score-ok "<사유>"`). 제출은 사용자 승인 뒤에만 한다.

## 6. 본선 발표와 보고서

- 결과서(모델링 보고서)는 `paper.md` 5절 집필 규칙을 따른다: 한국어 학술 문체, 용어 정의, [가정]/[문헌]/[계산] 표시, 표 캡션은 표 아래 `<p>표 n. …</p>`. 구성은 서식 순서를 따르고, 서식이 없으면 문제 정의 → 데이터와 검증 설계 → 방법 → 실험 결과(기준 모델 대비, 실패한 시도 포함) → 도메인 해석 → 한계(검증 데이터 사용, 비결정성) → 재현 방법.
- 수치는 모두 LEDGER와 `docs/changes/`의 실행으로 거슬러 올라가야 한다. 마무리 전에 평가표 기준으로 ContestEditor가 문체·문장을 다듬고, 코드는 러너의 기본 `reviewer`로 검토한다.
- 본선이 오프라인이면 일시·장소·참석 확인을 SUBMISSION.md와 사용자 묶음 질문에 넣는다. 발표 자료는 심사기준 순서로 만들고, 예상 질문(검증 데이터 사용, 일반화, 도메인 의미, 실패 사례)과 답을 `docs/presentation/QA.md`에 준비한다. 시연이 필요하면 맥에서 돌릴 수 있는 가벼운 추론 경로를 미리 확인한다.
- 대회가 끝나면 데이터 활용 서약대로 로컬·서버·저장소(검증 이미지가 든 그림 포함)의 데이터 사본을 파기하고, 파기한 곳과 시각을 README에 적는다. 결과 발표 뒤 `harness transition <id> closed --note won|lost|ended|withdrawn`.
