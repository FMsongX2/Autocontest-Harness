# Security

## Reporting a vulnerability

Use GitHub's private vulnerability reporting: **Security → Report a vulnerability** on https://github.com/FMsongX2/Autocontest-Harness. Please do not open a public issue for a vulnerability. Include the version (`ach --version`), the steps or input that trigger it, and what an attacker gains. You will get an answer within seven days.

## Threat model

The harness runs coding agents unattended on text it does not control: listing pages, official notices, organizer sites and emails. It also holds personal data (`data/profile.md`) and a GitHub login. The main risks and what the harness does about them:

| Risk | Mitigation | Limit |
|---|---|---|
| Shell injection through scraped titles, notes, receipts, or rule sources | Agents pass fetched text to the CLI through files (`add --from-file`, `--note-file`, and the JSON `--file` inputs of `checkpoint`, `rules`, `evaluation`, `submission`, and `submit`); only ids (`[a-z0-9-]+`) and CLI-issued tokens (`request_token`, `attempt_id`, observation tokens) appear on command lines. The CLI never runs file contents as commands. Collected items whose id is not lowercase alphanumeric are skipped. Titles are reduced to one line without control characters. The CLI runs `git`, `gh`, `orca`, `tmux`, and `python3 -m controllers` with argument lists, never through a shell | An agent can still ignore its instructions |
| Prompt injection from fetched pages | Every prompt treats fetched pages, listings, emails and registry text as data, not instructions, and tells the agent to report instructions found there instead of following them. Entry values in the launch prompt sit in a fenced data block | Models can still be manipulated; the CLI checks below are the backstop |
| Submitting or reading personal data without the user's consent | A submission intent, `submission start`, and `ach profile show --for <id>` require a valid `submit` approval. A submission approval is bound to the current work revision, the readiness record (including its `destination`), the scores, and the submission stage of the official rules; the intent and start refuse if any of them changed afterward, if a recorded file no longer matches its SHA-256, or if the intent's destination differs from the approved one, and the intent binds exactly the approved readiness files. A below-target score passes only through the typed history flag that `--score-ok` records, and only for your own approval; note text cannot bypass it. Approvals recorded before 0.7.0, and readiness records without a `destination`, do not authorize new submissions. `approve` refuses to run inside a contest session (`ACH_SESSION` is set by `ach launch`, `restart`, `resume`, and `recover`), so a contest session cannot approve itself or change `delegation`. Delegated approval is off by default, needs an explicit, revocable grant in the config, covers only submissions in its scope, and additionally needs tracked official rules and, from Level 2 up unless the video exemption applies, a final score bound to a verified independent assessment; revoking it stops any delegated approval not yet used from authorizing a submission or a profile read. The CLI re-checks eligibility, the persona guard, the scope, and the request token under the registry lock, and never delegates fees, new accounts, new consents, new signatures, or Level 5 plan approval. Level 5 plan reviews move on only through your own `approve`, and `ach recover` never moves `plan_review` | A session that clears the environment variable can bypass the check; approval is a safety catch, not a sandbox. Delegated approval judges structured records and hashes, not the quality of the deliverable. Run sessions with your harness's own permission controls |
| Duplicate or silent submissions | `submission start` saves `dispatching` before any external action, and a second start always fails. A timeout, lost response, or crash is recorded as `unknown` and blocks new intents, recovery, and cleanup; only receipt evidence (`ach submit --attempt`) or positive evidence that nothing arrived (`submission resolve`) settles it, and there is no `--force`. Confirmation needs receipt files under `.private/` whose hashes match | The CLI does not read the meaning of a receipt; a human or agent must look at an official channel |
| Stale or altered contest rules | Official sources are kept as immutable, content-addressed snapshots of the actual bytes; a changed hash becomes a pending review, and only categories whose reviewed values changed invalidate evidence. Rules fetched without a local file use a bounded GET with no cookies, credentials, or login, and URLs with user info are refused | A human or agent still has to read the source and record typed rules; ambiguous reviews stay pending |
| Leaking identity or prior scores into an independent assessment | Evaluation packets refuse `.private/`, `.harness/`, `JUDGE.md`, and profile files, copy only declared sanitized files under neutral labels, and keep the source binding private | The CLI hides metadata only; identity inside documents must be removed by the caller, who attests to it |
| Concurrent or outdated automation | Controllers check `ach contract --json` for protocol 2 before any write, hold a non-blocking lifetime lock (a second instance exits 75), and get the running binary through `ACH_BIN`. Reconcile observes and stores only; recovery reopens only a confirmed-missing session under a matching observation token. Controller logs contain codes and statuses, not private notes or receipt text | A process that ignores the lock or edits `data/` directly bypasses these checks |
| Publishing private work | Contest repositories are created private with Actions disabled. `route` refuses an existing repository that is public, or that belongs to another contest. Session logs, launch prompts and `.private/` are git-ignored in contest folders | Making a repository public for a submission is a manual step |
| Leaking personal state from the harness checkout | `data/` holds personal state, is git-ignored, and is created with mode 0700 and files 0600. Release binaries are built with local paths removed | Back up `data/` yourself |
| Path traversal in cleanup | `clean` archives only paths inside the contest folder and moves only folders that `route` created | |
